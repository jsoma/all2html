# Counter: Temporal Media Proposal

This document is a response to [PROPOSAL.md](PROPOSAL.md). The proposal is architecturally thoughtful and the reverse-engineering work is solid. The counterargument is not "don't do this" — it is "the proposal underestimates the cost, overgeneralizes from the evidence, and should be scoped differently."

## 1. The Two Examples Are Not The Same Pattern

The proposal treats `bars.html` and `tulsa.html` as evidence of a single reusable `scrollingparty` component family. They are not.

**bars.html** is a structured, data-driven temporal media piece:

- Serialized JSON config with `frameRate`, `frameLength`, `scrollStart`, `scrollEnd`
- External tracking JSON files (`tracking-desktop.json`, `tracking-mobile.json`) that drive overlay timing
- Video renditions served at multiple responsive widths (758, 960, 1098, 1280, 1600)
- Annotations positioned as side-panel text with `percent`-based scroll triggers and `alignSlide` layout
- A Svelte hydration architecture

**tulsa.html** is a content-driven narrative page:

- No serialized scrollingparty JSON config
- No external tracking JSON
- No frame-level synchronization
- Annotations are plain DOM elements with CSS-driven visibility
- Multiple independent scrollingparty sections (`topper`, `chapter-2-business`, `chapter-2-characters`, `chapter-3-greenwood`), each with different content types including 3D model references
- A `window.setupInteractive` hook pattern, not Svelte

The DOM class names (`g-scrollingparty-container`, `g-scrollingparty-annotations`) are shared, but the underlying data models and runtime behaviors are fundamentally different. The bars page uses frame-accurate video scrubbing with sampled overlay tracks. The tulsa page uses scroll-triggered visibility on static DOM nodes with lazy-loaded images.

Building a data model that covers both would either be too generic to be useful or would silently privilege the bars pattern while leaving the tulsa pattern as a degenerate case.

## 2. The Tracking JSON Is The Hard Part, And It Is External

The proposal's most compelling evidence — the `stage` / `layers` / `animatedTransforms` structure — comes from external tracking JSON files hosted on NYT's CDN. These files are not in the HTML. They are not authored by hand. They are almost certainly generated by a bespoke NYT pipeline that includes After Effects, a custom exporter, and internal tooling.

The proposal acknowledges this ("This is likely a derived browser format, not a direct AE project representation") but then proceeds as if designing the authoring format solves the problem. It does not. The authoring format is only useful if something can produce it. The proposal has no concrete answer for what that something is.

"Extract named text layers as annotations" is not an export strategy. It is a sentence that elides:

- How to detect which AE layers are annotations vs. motion graphics
- How to handle text animators with range selectors
- How to resolve expressions on Source Text or animated properties
- How to handle nested precomps and guide layers
- How to bake keyframes with cubic bezier easing to sampled arrays
- How to handle AE markers as timing cues
- Whether the exporter runs inside AE (ExtendScript/CEP/UXP) or outside (Bodymovin JSON, rendered output + metadata sidecar)

The Illustrator exporter is ~1,800 lines of ExtendScript for a tool whose data model is comparatively simple (static layers, character runs, artboard coordinates). An After Effects exporter that handles temporal transforms, keyframes, expressions, and text animators would be substantially more complex — and AE's scripting environment has different constraints than Illustrator's.

## 3. The Shared Primitives Overlap Is Smaller Than Claimed

The proposal lists these as shared between static and temporal content:

- Assets
- Text content
- Text style
- Geometry primitives
- Transforms
- Breakpoints / responsive variants
- Metadata and accessibility
- Output settings

In practice, the overlap is thinner:

**Assets** — yes, but temporal media assets include video renditions at multiple resolutions, poster frames, and frame sequences. The current `Asset` type is `{ id, path, width?, height? }`. Temporal assets need codec, frame rate, duration, and resolution variants. These are different enough that sharing the type would mean either a bloated base type or a discriminated union that's asset-in-name-only.

**Text content** — partially. The current `RichText` model is paragraph/run-based with character styles, hyperlinks, and effects. NYT's temporal annotations are flat strings with a `text` field and optional `altText`. Forcing temporal annotations through the paragraph/run model adds complexity for no benefit. And if temporal annotations ever need AE-style text animators (per-character transforms), the paragraph/run model is the wrong abstraction anyway.

**Text style** — partially. The bars annotations use simple CSS (`fontFamily`, `fontSize`, `color`). The full IR text style model includes `tracking`, `baselineShift`, `verticalAlign`, `textDecoration`, `effects[]` — none of which appear in the temporal examples. Sharing the type means temporal consumers must handle fields that will always be empty.

**Transforms** — no. Static IR transforms are `{ x, y, width, height, rotation, opacity }` in absolute pixels. Temporal transforms are `{ pos, anchor, scale, rot, opacity }` in normalized coordinates with optional per-frame sampled arrays. These are structurally different.

**Breakpoints** — partially. Static breakpoints are artboard-width-based grouping. Temporal breakpoints are separate media/tracking file sets per device class. The mechanism is different even if the concept overlaps.

**Metadata** — yes, this genuinely shares.

**Settings** — mostly not. Static settings control CSS output, positioning mode, responsive behavior, custom CSS/JS injection. Temporal settings control playback mode, scroll trigger points, frame rate, video rendition URLs. The overlap is `slug` and `metadata`.

Honest accounting: `metadata` and some settings genuinely share. Everything else is either structurally different or artificially unified at the cost of type bloat.

## 4. The Pipeline Cannot Be Shared

The current pipeline is a strict seven-step transform chain:

```
loadAndValidateIR → resolveSettings → computeBreakpoints → computeStyles
  → deduplicateStyles → computePositions → groupArtboards → emitter
```

Every step assumes artboards are static spatial structures with positioned elements. Temporal content would need a parallel pipeline:

- Frame rate / duration validation (no static equivalent)
- Keyframe interpolation or sample array generation (no static equivalent)
- Playback controller configuration (no static equivalent)
- Annotation timing validation (no static equivalent)
- Style computation is simpler (flat CSS, no paragraph/run deduplication)
- Position computation is different (normalized coordinates, not absolute pixels)

The proposal's suggestion to "add a temporal branch" implies a fork point somewhere in the pipeline. But there is no natural fork point — the divergence starts at validation and continues through every subsequent step. This is not a branch. It is a second pipeline that happens to share a Zod validator and an emitter registry entry point.

That is fine architecturally, but calling it a "branch" understates the work. It is a new pipeline.

## 5. The Authoring Format Solves A Problem That Doesn't Exist Yet

The proposal's central design contribution is the sparse authoring schema with keyframes that can be compiled to sampled runtime arrays. This is a clean design, but it solves a problem that currently has no producer and no consumer.

- **No producer:** There is no AE exporter. There is no manual authoring tool. There is no pipeline that generates temporal IR files. The proposal suggests hand-authoring test files, but hand-authoring sampled motion tracks with dozens of `[x, y]` pairs is not a realistic authoring workflow.
- **No consumer:** There is no temporal emitter. There is no playback runtime. There is no scroll controller. Building the authoring format first means designing a schema in the absence of the constraints that actually matter — what the exporter can extract and what the runtime needs to render.

The existing static pipeline was built IR-first, and that worked because the IR was designed alongside the Illustrator exporter that produces it and the HTML emitter that consumes it. The constraints flowed in both directions. Designing a temporal IR without either end of the pipeline is designing in a vacuum.

## 6. The Keyframe Model Is Underspecified

The proposal includes a keyframe motion form:

```json
{
  "kind": "keyframes",
  "frames": [
    { "t": 20, "value": [0.329, 0.393] },
    { "t": 61, "value": [0.301, 0.365] }
  ],
  "easing": "linear"
}
```

This raises questions the proposal does not address:

- **Easing model:** AE uses per-keyframe cubic bezier curves with independent spatial and temporal easing. "Linear" is listed as a string enum value. If the authoring format supports keyframes, it needs a real easing specification — even if initially limited. Otherwise the keyframe form is a trap: it looks like it supports authored motion, but it can only represent linear interpolation, which is visually wrong for most real animations.
- **Per-keyframe vs. global easing:** The `easing` field is at the motion level, not per keyframe. AE and CSS both support per-keyframe easing. This design decision should be explicit, not accidental.
- **Interpolation type:** Position interpolation can be linear or bezier-path (AE supports spatial bezier curves separate from temporal easing). The proposal does not distinguish.
- **Compile-to-samples as escape hatch:** The proposal's answer to all of this is "compile to sampled arrays." But if keyframes always get compiled to samples, why have keyframes in the authoring format at all? The value of keyframes is that they're sparse and editable. If they immediately lose fidelity during compilation (because the easing model is underspecified), they're worse than just storing the samples directly.

## 7. Playback Controller Ownership Is Unresolved

The proposal lists four playback modes (`scroll`, `autoplay`, `stepper`, `manual`) but does not specify who ships the playback runtime.

The current `standalone` emitter produces self-contained HTML files with no external dependencies. If temporal output follows the same pattern, `all2html` must ship:

- A scroll-to-frame mapping engine
- A video playback controller (or canvas frame renderer)
- An annotation overlay manager
- Responsive breakpoint switching logic
- Intersection observer setup for scroll triggers

This is not a template. This is a runtime library. The proposal does not acknowledge this or estimate its complexity.

If instead temporal output assumes an external runtime (GSAP ScrollTrigger, a NYT-style `scrollingparty.js`, a custom Svelte component), then the emitter is a data serializer, not an HTML producer. That's a valid choice, but it changes what `all2html` is — from a tool that produces ready-to-publish output to a tool that produces data for another tool's runtime.

## 8. Normalized Coordinates vs. Absolute Pixels

The proposal's annotation examples use normalized coordinates (`pos: [0.42, 0.39]`). The existing IR uses absolute pixels for all positions. The proposal does not address:

- Whether the temporal IR uses normalized coordinates as its canonical format
- Whether the compiler converts between coordinate systems
- How font sizes interact with normalized positioning (a `fontSize: 16` annotation at `pos: [0.5, 0.5]` on a 1920x1080 stage vs. a 640x360 stage renders at very different relative sizes)
- Whether responsive variants can use different coordinate systems

This is not a minor detail. The static IR's choice of absolute pixels is load-bearing — it enables pixel-accurate positioning that matches the design tool. Normalized coordinates enable responsive scaling but lose pixel accuracy. The proposal should commit to a convention and explain the tradeoffs.

## 9. The Scope Is v2, Not v1.x

The project's own SPEC.md lists v1.1+ deferred features as:

- SnippetElement rendering
- Tagged text bindings
- CSS custom property images
- Artboard change callbacks

The project's PROGRESS.md shows that Figma support — a plugin for an existing, well-documented design tool with a stable API — is still gated as beta after significant hardening work.

Temporal media support requires:

- A new IR schema branch
- A new pipeline (not a branch of the existing one)
- A new emitter with an embedded playback runtime
- A new exporter for a tool (After Effects) that the project has never targeted
- A new testing corpus with frame-accurate playback validation
- A new hardening process for a fundamentally different output type

This is not a v1.1 feature. It is not even clearly a v1.x feature. It is a v2 scope expansion that changes what the project is — from a static/responsive graphics tool to a temporal media authoring system.

## 10. What Should Happen Instead

### Step 0: Finish what's started

The Figma plugin is beta. The Illustrator panel is in active development. SnippetElement is specced but unimplemented. Finish those before starting a new workstream.

### Step 1: Study the problem from the consumer side

Before designing the authoring format, build a minimal scroll-video player that consumes the NYT tracking JSON format directly. Load the bars tracking JSON, render a `<video>` element, scrub on scroll, overlay annotations. No IR, no pipeline, no schema. Just a standalone prototype that proves the runtime works.

This answers the questions the proposal leaves open: what does the playback controller need? What are the actual runtime constraints? How does responsive switching work in practice?

### Step 2: Study the problem from the producer side

Before designing the exporter, manually recreate one of the NYT examples in After Effects and try to extract the annotation data. What does AE's scripting API actually give you? Can you get layer transforms at arbitrary frames? Can you enumerate text layers by naming convention? What are the real extraction constraints?

This answers the question the proposal waves away: what can an AE exporter realistically produce?

### Step 3: Design the IR from both ends

With a working consumer prototype and a working producer prototype, design the temporal IR to fit between them. The format should be whatever the producer can emit and the consumer can render — not an idealized schema designed in isolation.

### Step 4: Then write the proposal

A revised proposal, informed by Steps 1-3, would have:

- A concrete runtime architecture (not "possible modes: scroll, autoplay, stepper, manual")
- A concrete exporter scope (not "extract named text layers")
- A data model shaped by real constraints (not aesthetic preferences about sparse vs. sampled)
- An honest cost estimate

## Summary

The proposal correctly identifies temporal media as a valuable direction for the project. The architectural instinct — separate scene structures, shared primitives, authoring vs. runtime formats — is sound in broad strokes.

But the proposal is premature. It designs a schema without a producer or consumer. It overstates the shared-primitive overlap. It underspecifies the keyframe model, the playback runtime, the coordinate system, and the exporter. It treats two structurally different NYT examples as evidence of a single pattern. And it scopes a v2 initiative as if it were a natural extension of the current pipeline.

The right next step is not to design a temporal IR. It is to build two small prototypes — one consumer, one producer — and let the IR design emerge from what those prototypes actually need.
